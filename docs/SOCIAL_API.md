# Social API

All endpoints require the authenticated `ta_session` cookie. Mutations require same-origin requests; JSON requests return `{data:...}` or `{error:...}`. Names below omit `/api`. UUIDs identify users, rooms, servers, messages, polls, and parties. Private settings, friend notes, school resources, emails, and session material never appear in public profiles.

## Profiles, friends, notifications

- `POST profile`: editable `displayName`, `bio`, `status`, `avatar`, `banner`, `settings`. Authority fields (`role`, `xp`, identity) are rejected. Settings allow appearance, presence, privacy, notifications, accessibility, game audio preferences and persistent Focus Mode; nested settings merge under a row lock. A database constraint keeps settings as JSON objects.
- `GET users?q=...`: bounded safe user search. `GET users/:userId`: public profile, opted-in friends/activity, and `isFriend`; blocked profiles are unavailable.
- `GET friends`: `{friends,incoming,outgoing,blocked}`; only the requesting user sees their nickname/note/favorite/close-friend/mute preferences.
- `POST friends/request {userId}`: sends a request. `POST friends/:userId/accept|decline|cancel|remove|block|unblock`: directional request actions and accepted friendship/block operations. `POST .../preferences {favorite?,closeFriend?,muted?,nickname?,note?}` requires accepted friendship. `POST .../mute {muted}` also works for other users.
- `GET friends/suggested`: bounded mutual-friend suggestions based on real friendships.
- `GET home`: current friends, recent personal notifications, and intentionally published activity by the user/their friends. No school data.
- `GET notifications`: newest 100 personal notifications. `POST notifications/:id/read` and `POST notifications/read-all` update only the current inbox. Notification kind preferences, user mute, and blocks suppress direct notifications.

## Chat

- `GET chat/global`: global room descriptor. `GET chat/rooms`: own DMs/group DMs with members, preview, and unread count. `POST chat/rooms {userIds,name?}` creates a DM or group (maximum eight members); DMs deduplicate by canonical member pair. Privacy and pairwise blocks apply.
- `GET chat/:roomId/messages?limit=50&before=:messageId&q=...&pinned=true`: oldest-first page, `{room,messages,nextCursor}`. `global` is accepted instead of the global UUID. Pages cap at 100; search uses indexed text search. Normal room history excludes dedicated thread replies; search and pinned results include them with `threadId`. Root messages include a count of visible, nondeleted thread replies. Cursor/replies must reference the same room and conversation. Author identities, timestamps, reply IDs, reactions, pin status, attachments, and poll results accompany messages. Deleted messages retain a tombstone with empty content. Blocked authors are hidden.
- `POST chat/:roomId/messages {content?,replyTo?,threadId?,attachmentIds?,poll?}`: durable messages; poll `{question,options:[string],multiple?,closesAt?}`. `threadId` identifies a root room message and creates its dedicated thread on the first reply. Nested reply references must remain within that thread. No chat XP. A database lock enforces ten sends per ten seconds across rooms and threads.
- `GET chat/:roomId/threads/:rootMessageId?limit=50&before=:replyId&q=...&pinned=true`: authorized thread history using the same pagination, filters, tombstones and message features; response adds `thread:{id,root}`. A root must belong to this room and cannot itself be a thread reply. `root` becomes null if its author's account removal physically deletes the original message; other authors' replies remain in their thread.
- `GET chat/:roomId/threads`: compatible array of recent conversations. Add `page=true&limit=50&before=:threadId&q=...&archived=true&following=true` for `{threads,nextCursor}` pagination; limits cap at 100. Summaries include names, archive status, visible reply counts, exact last activity, following state and separate unread counts. Named/owned/followed empty threads and preserved conversations whose root was removed remain discoverable. Membership, blocks, restricted channel roles and announcement send permissions apply to thread reads and writes.
- `PATCH chat/:roomId/threads/:rootMessageId {name?,archived?}`: thread creator, group owner, server message manager or platform moderator may rename/archive/unarchive; archived threads remain readable and reject new replies. `POST .../:rootMessageId/follow {following}` subscribes or explicitly unsubscribes, with a maximum 1,000 followers per thread. A reply auto-follows its author unless they previously unfollowed. Authorized followers receive preference-aware thread notifications. `POST .../:rootMessageId/read {messageId?}` advances a monotonic, thread-scoped read cursor without marking the main conversation read.
- `PATCH chat/messages/:id {content}`: author-only edit. `DELETE chat/messages/:id`: author, channel message manager, or emergency platform admin. `POST|DELETE .../:id/reactions {emoji}` applies current channel reaction permissions. `POST|DELETE .../:id/pin` requires channel manager, global admin, DM/group owner, or party leader.
- `POST chat/polls/:pollId/vote {optionIds}` replaces the voter's selection under a poll lock; closed/deleted polls, another room, invalid option IDs, and multiple votes in single-choice polls are rejected.
- `POST chat/:roomId/read {messageId?}`: a monotonic read cursor for the main conversation. `GET chat/:roomId/members` returns member-authorized group metadata and membership. `PATCH chat/:roomId {name?,icon?}` and `DELETE chat/:roomId/members/:userId` require the group owner; avatar URLs use HTTPS and can be cleared with null. `POST chat/:roomId/members {userId}` adds an enabled account subject to eight-member capacity, privacy and pairwise blocks. `POST chat/:roomId/leave` removes oneself, transfers ownership to the oldest remaining member (UUID breaks ties), or deletes an empty room. Removed/departed users lose access and thread subscriptions. Group membership changes and message/thread writes serialize on the room row.
- `POST chat/:roomId/files` uploads multipart field `file` to private storage; the response is `{id,filename,mime,bytes}`. Bind IDs in the next message's `attachmentIds`. Binding is atomic and requires an unused upload owned by the author in the same room. School attachment IDs cannot bind.
- `GET chat/files/:attachmentId`: private download with current room authorization, block checks, and a nondeleted parent message (or uploader-only access before binding). Metadata/signature validation rejects active/unsupported formats. Configured `MAX_CHAT_FILE_BYTES`, `MAX_CHAT_IMAGE_BYTES` and storage `MAX_FILE_BYTES` apply. Chat and school uploads share the administrator-configurable quota (default 2 GiB), including trash and pending uploads. Formats include validated images/documents plus MP3, WAV, WebM and MP4/M4A. `DELETE chat/files/:id` discards an owned unbound upload through a durable deletion queue; published attachments cannot be removed this way.

The browser composer supports multi-file upload progress, protected images/audio/video, downloads, and microphone-triggered voice recording capped at 60 seconds. Start a thread from a room message, open it from its reply count or a search result, or use the searchable paged browser with archive/follow filters. The dedicated composer reuses attachments, polls, editing, deletion, reactions and replies. Live events update thread metadata and room reply counts; reconnect fetches durable history. Group settings expose owner-authorized rename/avatar/add/remove and member leave controls. Individual `@username` mentions notify only users with room access. `@everyone`/`@here` in server channels require the explicit permission, but do not fan out notifications yet.

- `GET chat/gifs?q=...` returns `{configured,provider,results,message?}`. Without `GIF_PROVIDER=giphy` and `GIPHY_API_KEY`, it returns an unavailable state and makes no provider request. Configured searches use the fixed HTTPS GIPHY endpoint, no redirects, a five-second timeout, 512 KiB maximum response, 120-character query and at most 12 safe results; returned image/source URLs require HTTPS GIPHY hosts without credentials. The UI disables unavailable search, inserts selected image URLs, and renders recognized GIF links. Live provider results require a valid deployment key; tests use an injected provider response, not fake application results.

- `POST chat/link-preview {roomId,messageId}` loads a title/description preview only after an explicit browser action. The server derives the first HTTPS URL from the stored, nondeleted message; active account, room view/embed permissions and blocks are checked before fetching and again before returning metadata. Wrong-room IDs and edited messages are rejected. Only HTTPS port 443, public DNS names and public unicast IPv4/IPv6 answers are accepted. Every redirect (maximum three) repeats validation, and sockets pin a vetted address while retaining normal hostname/TLS certificate verification. Literal IPs, credentials, local/internal names, private/link-local/metadata/special ranges and mixed public/private DNS answers are rejected. Total DNS/network time caps at four seconds, bodies at 64 KiB, headers at 8 KiB; compression and non-HTML/unsupported character sets are rejected. Scripts, HTML and remote images are never rendered. Small text metadata uses a per-process, per-user/message/content cache of at most 256 entries for five minutes. A Redis budget limits previews to ten per user and 200 globally per minute; missing Redis fails closed. External live fetching depends on deployment DNS/egress, while unavailable targets retain their ordinary message link.

Stickers remain unimplemented. Preview caches are temporary and do not add persisted database metadata.

## Servers

- `GET servers`: joined server summaries. `GET servers/discover?q=...`: discoverable summaries matching name/description/tags. `POST servers {name,description?,discoverable?,tags?}` creates owner membership, default member role, and `general` channel.
- `GET servers/:id`: member-authorized server detail, visible channels, roles, member identities/role IDs, and current effective permissions. Private server details never appear in discovery.
- `PATCH servers/:id` edits metadata with `manage_server`; `DELETE` requires ownership. `POST .../owner {userId}` transfers to a current member. `POST .../leave` requires transfer first for the owner. `POST .../join` joins discoverable servers.
- `POST .../channels {name,type?,position?,restrictedRoleId?}` and `PATCH|DELETE .../channels/:channelId` require `manage_channels`. Restricted roles must belong to the server. Announcement messages require `manage_messages` as well as normal send permissions.
- `POST .../roles {name,color?,position?,permissions?}` and `PATCH|DELETE .../roles/:roleId` require `manage_roles`, can grant only held permissions, and can only alter lower roles unless owner. Default role cannot be deleted. Roles used to restrict channels require deliberate channel reconfiguration before deletion. `POST|PATCH .../members/:userId {roleIds}` checks the same hierarchy; `DELETE` requires `manage_server` and a lower target role. Ownership cannot be removed through role assignments/kicks.
- `GET|POST .../invites`: list/create `{expiresInHours?,maxUses?}` with `create_invite`. `DELETE .../invites/:code` revokes own invite (server managers can revoke any). `GET invites/:code` gives only a safe preview; `POST invites/:code/join` atomically validates expiration and consumes a limited use only for new membership.
- `GET servers/:id/emojis` lists member-authorized metadata. `POST servers/:id/emojis` accepts multipart `name` and `file` with `manage_server`; names use 2–32 lowercase letters/digits/underscores. PNG/JPEG/GIF/WebP uploads require matching filename, MIME and signature, dimensions up to 512 × 512 pixels, and at most 256 KiB; SVG is excluded. The server cap is 50, enforced under a server row lock. Bytes are stored in the database, count toward the uploader's shared storage quota, and use the same user lock as other quota reservations. `GET .../emojis/:emojiId/file` streams private raster bytes with current membership and `nosniff`; `DELETE .../emojis/:emojiId` requires `manage_server` and releases quota. Server ownership controls these assets even when uploaded by another manager. Chat renders stable `:emoji:<uuid>:` tokens using the current channel's server, with an unavailable fallback for deletion or missing access; deletion events refresh existing messages. Full image decoding/transcoding and sticker support are not implemented.

Permissions: `view_channel`, `send_messages`, `attach_files`, `embed_links`, `add_reactions`, `mention_everyone`, `manage_messages`, `manage_channels`, `manage_roles`, `manage_server`, `create_invite`. Default role permissions combine with explicitly assigned roles. Owners hold every permission. Channel restriction is one required role, kept intentionally simple.

## Parties

- `GET parties`: `{party,invites}`; `POST parties {}` creates a durable global party/chat. A user can belong to only one party and the maximum is eight.
- `GET parties/:id`: member-only recovery. `POST .../invite {userId}` checks all current members' blocks and notifies the invitee. `POST .../join` requires a valid invite and checks capacity atomically. `POST .../decline` declines an invite.
- `POST .../leave`: removes self, transfers leadership to the oldest remaining member, or deletes an empty party. `POST .../kick {userId}` and `POST .../leader {userId}` require the current leader. Membership/game changes reset readiness.
- `POST .../ready {ready}` sets self readiness. `POST .../game {gameId}` selects an implemented game (or null); `POST .../launch {}` requires leader, a selected game, all members ready, and game player limits. It returns `{partyId,gameId,route,multiplayer}`; actual multiplayer lobby creation uses the realtime `party:launch` protocol.

## Realtime and limits

`authorizeRoom(userId,roomId,permission)` is shared with the realtime service and reevaluates current room/member/role/block state. Durable operations publish optional Redis events to `tell-aviv:events`: message create/update/delete, reactions, friend changes, party updates/invites, and notifications. HTTP polling remains functional without Redis. Separate user-scoped durable limits protect friend requests, DM/server creation, invitations, and file uploads. No automated content moderation, email delivery, or profanity filtering is introduced.

## Validation

`RUN_DB_TESTS=1 pnpm exec vitest run tests/social.test.ts` runs persisted profile, directional request/private-note, block/DM, server invitation race/role/channel, party leadership/readiness, and poll authorization tests against a migrated local/disposable database. Tests create their own identities and clean up domain records. Pure projection/permission tests run without a database.

`RUN_DB_TESTS=1 pnpm exec vitest run tests/chat-threads-database.test.ts` verifies thread isolation/search, private access and reply scope, scoped pagination, root removal preservation, blocks, announcement permissions, attachment binding/download authorization and the shared flood limit. `pnpm exec playwright test tests/e2e/chat-threads.spec.ts` exercises private live replies, attachments, separate room history and recovery after deletion of the root author's account.

`tests/chat-organization-database.test.ts` covers naming/archive authorization, subscriptions/unread, explicit unfollow, pagination beyond 50, group ownership/transfer and privacy. `tests/server-emoji-database.test.ts` covers manager/member permissions, private bytes, malformed/oversized images, concurrent count/quota reservations, deletion and cross-server isolation. `tests/chat-media.test.ts` covers image dimensions and bounded/disabled provider behavior. Browser cases `tests/e2e/chat-organization.spec.ts` and `tests/e2e/chat-media.spec.ts` exercise live group/thread controls and real image upload/render/delete with the unavailable GIF state.
