# Architecture

Tell Aviv is a modular monolith plus a realtime service. Next.js owns the authenticated web and REST API. Domain handlers in `packages/platform` own social, classes/creations, games/economy and admin authorization. PostgreSQL is canonical durable state, including recovery checkpoints and queue/economy journals; Redis stores live presence/lobbies and realtime signals. No game receives private messages, school materials, or authentication secrets.

`packages/auth` authenticates opaque cookies against hashed database session records; native credentials use Argon2id, credential versions, transactional one-use recovery and recent-auth guards. `packages/database` provides postgres-js parameterized SQL, Drizzle typed identity schema, and immutable/checksummed transactional SQL migrations. Domain migrations normalize their core relationships; structured note/level/game payloads use versioned JSON.

`games/catalog.ts` contains pure manifests. Client engines are dynamically loaded through `GamePlayer`. They use `@tell-aviv/game-sdk` for identity, namespaced saves, presence, lifecycle, validated game actions and leaderboard reads. Server-owned economy and progression live in `games/server` with transactional persistence in the game domain. Casual browser physics/action saves do not mint ranked rewards.

School resources are private unless an explicit per-resource share grants view/edit. Binary uploads are validated and stored outside executable web directories, and every download passes session/resource authorization. Community level publication is independent of school sharing and uses bounded structured objects, never executable user scripts.

`packages/creator-runtime` isolates schema compatibility, deterministic physics and the bounded logic interpreter shared by the editor and server replay. Creator discovery and verified attempt persistence are separate modules. Classes uses school-only model modules, math rendering and private study/history services. Social organization, custom media and secure link transport are extracted from the main handler; the preview transport is pinned to validated public DNS answers and is explicitly invoked for an authorized stored message.

Realtime store/queue code uses a per-namespace worker lease, lobby locks, public identity whitelists and per-player state projections. Immediate board/poker checkpoints and journaled stakes differ from periodic combat snapshots. Marketplace offers and poker settlements use dedicated transactional modules. Background operations own age-gated reconciliation, deletion retries, guarded consistent backup copying and retention. API errors carry stable codes/correlation IDs; metric labels are bounded and never retain private payloads.

Development services bind loopback and are managed by `scripts/local-services.sh`; production uses normal HTTPS reverse proxy routes for web and Socket.IO, including long-poll fallback. The initial architecture targets a small community of roughly 15–20 users. Local mixed-load checks cover four fixture accounts, application writes, trades and realtime games, with measured latency and isolated cleanup; these diagnostics do not establish deployed capacity. See [reliability evidence](RELIABILITY_3.md).
