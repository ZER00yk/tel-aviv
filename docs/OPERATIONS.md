# Scheduled maintenance and storage integrity

Run `pnpm exec tsx --env-file=.env scripts/ops-worker.ts --once --dry-run` to inspect the current maintenance plan. Dry runs do not expire trash/offers, send reminders, enqueue orphan deletion, remove backups or persist sweep state. The trusted worker accepts `--loop --apply` for scheduled execution. Do not expose these commands as user-callable HTTP endpoints.

Each pass is serialized with a PostgreSQL advisory lock and performs bounded batches: up to 100 accounts/resources by default, with pagination cursors stored in `operation_state`. It delivers private school reminders, removes school trash after the existing 30-day policy, retries physical deletion jobs, expires elapsed casino offers/refunds reservations, refunds abandoned poker escrow after the guarded 24-hour policy, inventories uploads and reports missing/size-mismatched objects. Worker status records the last pass, failures and safe error codes; admin health reports retry counts/oldest job, integrity counts and worker state. Failed operations retry on the next pass without marking their sweep complete. Signals stop the loop between work and short waits.

Configuration:

| Variable                                    | Default                               | Behavior                                                             |
| ------------------------------------------- | ------------------------------------- | -------------------------------------------------------------------- |
| `OPS_INTERVAL_SECONDS`                      | `60`                                  | Delay between scheduled passes, 10–3600 seconds                      |
| `BACKUP_ENABLED`                            | `false`                               | Enable automatic snapshot creation after configuring clients/storage |
| `BACKUP_EVERY_HOURS`                        | `24`                                  | Snapshot interval, at least one hour                                 |
| `BACKUP_PATH`                               | `/workspace/tell-aviv-backups`        | Private backup directory                                             |
| `BACKUP_RETAIN_DAYS`                        | `14`                                  | Age cutoff for verified managed snapshots                            |
| `BACKUP_MIN_KEEP`                           | `7`                                   | Minimum verified completed snapshots, at least two                   |
| `PG_DUMP_BIN`, `PSQL_BIN`, `PG_RESTORE_BIN` | Local extracted 17 tools or host PATH | PostgreSQL client executable overrides                               |

Cron/systemd can run the one-shot apply command. The loop provides the same scheduler without a separate cron daemon. The production Compose `operations` service selects the Dockerfile `operations` target, which combines the app/Node executable with the PostgreSQL 17 Bookworm client image, shares private uploads and mounts a persistent backups volume. That recipe enables the daily/14-day/minimum-seven policy through environment settings. The normal app image stays the default build target. Both images have now been built and exercised on an isolated Docker production copy: maintenance dry-run reported zero failures and verified five physical objects against five metadata records, and a fresh container-created backup passed an isolated PostgreSQL restore with 115 tables, 99 accounts, 36 migrations and five upload checksums. This validates the container clients and backup volume; continuous scheduler operation and a separate off-host target still require their own evidence.

The October 4 cloud deployment's post-pacing dry run also passed with zero failures and five objects matching five metadata records. A scheduler startup completed one applied pass with zero failures and produced a fresh verified snapshot, but its VFS container allocation exhausted more than 3.2 GB of available disk despite the image's 1.59 GB logical size. Only that new container was stopped and removed; the application services, data volumes, images, and snapshots were preserved. The scheduler remains stopped, so two-pass or daily scheduling is not established. A host-worker fallback can reach the private database and Redis addresses, but cannot access Docker-managed upload/backup volumes outside the permitted writable workspace. See the [deployment receipt](DEPLOYMENT_RECEIPT_GOALS_5.md) for actual counts, resource evidence, and deferred commands. Provide enough capacity for the observed allocation and an operational reserve, use a more efficient Docker storage driver, or provide supported access to the real production volumes before enabling continuous maintenance.

## Physical objects and metadata

`storage-reconcile.ts` defaults to a report-only inventory; `--apply` persists findings and queues eligible orphan bytes for the ordinary deletion outbox. Both local and S3 providers expose bounded pages and object HEAD metadata. Local inventory ignores symlinks, subdirectories and names outside app-generated UUID keys. S3 uses signed HEAD/ListObjectsV2 requests, bounds inventory XML to 2 MiB, ignores unrelated keys and rejects DTD/entity documents. Local offset pagination can revisit/skip files while a directory changes; repeated complete sweeps recover eventual coverage. Large deployments should use provider-native indexed inventory.

Objects without metadata become deletion candidates only after a 24-hour modification-time grace period. Under a per-key advisory lock, reconciliation rechecks both current metadata and provider HEAD before queuing deletion. Metadata binding takes the same lock and rejects a queued or missing object, including a stalled upload whose bytes were already removed. The cleanup worker independently protects referenced objects even if a mistaken cleanup job exists. Upload-metadata rollback attempts immediate deletion; provider failures leave durable retry jobs. A process crash or uncertain S3 PUT can leave physical bytes without metadata; the inventory sweep detects them after grace.

Missing bytes and size mismatches produce durable integrity findings. They never cause automatic deletion of school/chat metadata or private notes. Restore the object's bytes from a verified backup or resolve the affected resource deliberately. Findings resolve when repair/deletion is observed. Provider failures count as unavailable, not as evidence that objects are missing. A private generated write/HEAD/read/delete probe runs at most every ten minutes; failed probe cleanup enters the outbox and reports failure.

Local provider operations, isolated fixture reconciliation, late upload binding, cleanup protection, scoped scheduler retention/reminders and backup checksums/retention are tested. No unknown user data, global expired trash or orphan collection was deleted during verification. Authenticated encrypted envelopes and the mounted-filesystem destination abstraction are fixture-tested; see [encrypted backup operations](ENCRYPTED_BACKUPS.md). Live S3 credentials, a real off-host destination, remote lifecycle/versioning and production scheduler/load behavior remain deployment checks.
