# Backup and restore

From repository root, with PostgreSQL client tools installed, run `pnpm exec tsx --env-file=.env scripts/backup.ts`. This writes a v2 custom-format SQL dump, referenced upload bytes through the selected provider, and checksum manifest under `BACKUP_PATH` (default `/workspace/tell-aviv-backups`). Credentials are passed through PostgreSQL environment variables, never printed or stored in manifests. Set PG_DUMP_BIN when using host-installed clients. Scheduled creation and verified retention are configured in [OPERATIONS](OPERATIONS.md).

Restore into a **new empty database**, never reset the live one. Set `RESTORE_DATABASE_URL` securely and (if local upload data exists) `RESTORE_UPLOAD_PATH` to a new private directory. Run `pnpm exec tsx --env-file=.env scripts/restore.ts <backup-directory> --confirm-restore`. It verifies the checksum, rejects nonempty databases, and uses an atomic SQL restore. Verify migrations, row counts, authentication and protected file retrieval before updating application configuration. Client executable overrides PSQL_BIN/PG_RESTORE_BIN are supported.

The v2 workflow coordinates the SQL snapshot with immutable referenced bytes and application cleanup locks, and can copy through the S3 provider. It cannot prevent bucket lifecycle rules or another filesystem operator deleting bytes; such loss aborts the snapshot. [Optional AES-256-GCM envelopes and a mounted encrypted-destination interface](ENCRYPTED_BACKUPS.md) are implemented and fixture tested. Live S3/versioning, off-host infrastructure and deployed restore verification remain operations work.

Validated locally on 2026-10-03: backup `/workspace/tell-aviv-backups/2026-10-03T00-46-08-176Z` restored into an isolated throwaway database and upload directory, with 64 tables, 52 accounts and 13 migrations. The verifier removed only its own temporary restore targets; the source database remained intact. These counts describe that snapshot, not permanent production sizing.

The development-depth pass adds managed v2 snapshots. `scripts/backup.ts` exports a PostgreSQL repeatable-read snapshot, passes it to `pg_dump`, and copies only upload keys referenced by that same snapshot. An outer advisory lock is acquired before establishing that snapshot; physical retry cleanup takes a shared version of the same lock and waits while referenced bytes are copied. Metadata changes can continue. Each binary has a SHA-256/size entry in the private manifest; the database dump also has a streamed checksum. The snapshot is published by renaming its staging directory only after every referenced object is copied. Missing or size-mismatched bytes abort completion, preserve a failed staging directory for diagnosis and keep existing complete backups. Keys are immutable in normal app uploads. External bucket/filesystem deletion can still abort a backup; SQL/outbox coordination cannot stop an external actor. Long dump/copy operations hold a read snapshot and postpone physical deletion; schedule them outside busy periods.

Restore still accepts existing v1 snapshots. For v2 it verifies the dump and every upload before SQL restoration, rejects symlinked backup files and invalid keys, checks the destination database/upload directory, stages binaries first, restores SQL in one transaction, then publishes the staged upload directory. A failure during the final upload-directory rename can leave only the explicitly selected new database restored; do not switch application configuration until verification completes. Restoration does not reset or select the live database automatically.

Managed backup retention defaults to 14 days with at least seven verified complete snapshots retained. `pruneBackups` defaults to a dry run and only applies to completed v2 snapshots generated by this implementation. It verifies their manifests and checksums first. Legacy backups, unknown directories, failed/incomplete staging directories and corrupted snapshots are preserved for operator review. Retention tests create and delete only their own temporary snapshot directories. Backups contain private data and need restricted filesystem permissions, an operator-managed encryption key and an off-host copy policy in production.

V2 backups can copy referenced S3 objects through the configured provider, rather than copying a local directory. Provider versions and remote lifecycle policies still need deployment configuration. The S3 signing/list/HEAD paths are tested with mocked HTTPS responses; a live bucket has not been verified.
